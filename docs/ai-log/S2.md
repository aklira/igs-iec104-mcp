# S2 — Runtime, server role

## Prompt

Task S2 of `IMPLEMENTATION.md` §14: run the runtime as a station with the points of its
configuration, and an API to update a point. Done when an upstream client (or S1) interrogates the
station and receives a point updated through the API.

## Summary

The runtime runs as a client (`--connect`, S1) or as a station (`--listen ADDRESS --points FILE`).
The two roles are chosen on the command line, and each is refused by the other's routes (`409`).

- `points`: the points file, JSON with `schema_version: 1`. Each point has an address (1 to
  16777215), a kind (`single`, `double`, `normalized`, `scaled`, `float`), a value in the form of
  its kind, and `stamped`. Unknown fields, a wrong schema version, a duplicate address, and a value
  of the wrong form are refused with a message that names the point. The kinds map to the monitoring
  types of the profile (M_SP, M_DP, M_ME_NA, M_ME_NB, M_ME_NC, and their time-tagged forms).
- `server_role`: binds the station with the library's `Server`, registers the points, and refuses
  every command as an unknown address (cause 47). The configured command policy is task C3.
- `runtime`: a role is either a client engine or a station engine. A station runs its
  `run_until` with a five-second grace (task U1), stopped when the control API stops.
- `api`, station routes: `GET /v1/points`, `GET /v1/points/{address}`, `POST /v1/points/{address}`
  with `{"value": ...}`. An update answers `200` with the new value and whether it was queued (a
  change); an unknown address answers `404`, a value of the wrong form `400`.
- `GET /v1/ready` reports `role` (`client` or `station`), the listen address and the number of
  points for a station.

Dependencies: none added. The runtime already uses `serde_json`, and `serde` derives the points file.

## Verification

Automated (`cargo test --workspace --locked`): 29 unit tests (the points file, the configuration,
the event log, the client's status), 2 client-role tests (S1), and 2 server-role tests:

- `tests/server_role.rs`, first test: an upstream `igs_iec104::Client` connects to the station,
  starts the transfer, and interrogates it. Point 1 is `true` from the file. Then
  `POST /v1/points/1 {"value": false}` answers `200`, and the next interrogation reports `false`.
- `tests/server_role.rs`, second test: the station lists its five points, reports its role and
  addresses, refuses a boolean for a float point (`400`), answers `404` for an unknown point, and
  answers `409` to a client route.

Manual, with the real binaries: a station runtime (`--listen 127.0.0.1:2405`) and the S1 client
runtime (`--connect 127.0.0.1:2405`):

- The client's interrogation gives point 1 with the value on (`…01`), as the file says.
- `POST /v1/points/1 {"value": false}` on the station answers `queued: true`.
- The client's next interrogation gives point 1 with the value off (`…00`).
- SIGTERM stops both with exit status 0.

Gates: the Python gate passes; `cargo fmt --check`, `clippy -D warnings`, `cargo test` and
`cargo deny check` pass. The image builds with Podman, prints its identity, and rejects a missing
points file with a message that names it.

## Decisions and open points

- The points file is JSON for now. The definitions of the test bench are YAML (§5), and the
  controller writes the runtime's configuration; the schema is fixed with the contract in C1.
- Commands are refused for every point. The configured policy (accept, refuse, or refuse as unknown
  address, per point or per command type) is task C3.
- A point update needs a JSON body on the route. An empty request is refused by the extractor
  before the route checks the role, so a client that sends no body gets a plain-text error rather
  than `409`. C1 defines whether the body is required and what error it gives.
- The events of the station (connections, transfers) come from the upstream `ServerEvent` stream
  (U2), in task C3. S2 does not report them.
- The control API still has no credential (§3). C1 adds it.

## Size

The change is about 450 lines added and 190 removed in the runtime, plus 300 lines of tests: above
the roughly 400 lines that §2 allows per task. As with S1, it is one change because its acceptance
needs the whole path from the points file to the upstream client.

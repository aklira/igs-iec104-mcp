# D1 — Docker adapter and labels

## Prompt

Task D1 of `IMPLEMENTATION.md` §14: the Docker adapter off the event loop, labelled networks and containers,
and image digest checks. Done when the integration tests create and remove labelled resources and never touch
unlabelled ones.

## Summary

- `docker/labels.py`: the owner (project, bench, run), its labels (`dev.igs-iec104.mcp.*`), and `owns`, which
  checks the labels exactly.
- `docker/specs.py`: `NetworkSpec`, `ContainerSpec`, and `Limits`. A container spec has no field for a mount,
  a port, a privilege, the host network, or a capability. Names follow `igsmcp-<run>-<part>`. A tag is refused.
- `docker/adapter.py`: `DockerAdapter` over the Docker SDK, with each call run in a worker thread. It creates
  and finds networks and containers (idempotent for the same owner), lists and removes the owner's resources
  (containers first), checks an image by its digest, and provides `creating`, a block that rolls back the
  resources it created when it fails.
- D-015 records the labels, names, hardening, digest checks, rollback, and the typing of the SDK.
- `pyproject.toml`: a mypy override for `docker` (no type hints, so its names are `Any`), in the same way as
  `jsonschema`.

Dependency: the Docker SDK for Python, approved at B1 (§11). No new dependency.

## Verification

- `tests/unit/test_docker_specs.py`: the owner's names and run identity, the labels, `owns` (each missing or
  different label is refused), the resource names, network and container names, a tag refused, a digest
  accepted, the absence of mount and privilege fields (a call with `privileged=True` is a `TypeError`), and
  the limit bounds.
- `tests/integration/test_docker_adapter.py` (8 tests, against an engine): a labelled network and container are
  created, listed, and removed; the container's hardening is read back from the engine (not privileged,
  read-only root, no binds, memory, processes, CPUs, capabilities dropped, none added); creating again finds
  the same resources; an unlabelled network and an unlabelled container with the names of the run are refused
  and kept; another run's resources are kept; a failed creation removes what it made; the image digest checks.
- Run against Podman's Docker-compatible socket (`DOCKER_HOST=unix:///run/user/1000/podman/podman.sock`), since
  Docker is not installed here. Podman lists each capability it drops, where Docker lists `ALL`; the test
  accepts both. No labelled resource was left behind.
- Gates: `ruff format`, `ruff check`, `mypy` (strict, 45 source files), unit tests (181 pass), the licence check.
  The Docker integration tests are not yet run in CI on Docker itself; the `integration` job of CI has Docker,
  and will run them on the next push.

## Decisions

- D-015: labels, names, hardening, image digests, rollback, and the SDK's typing.

## Points for the next tasks

- D2 (the lifecycle) uses `creating` for the network and the containers, then starts the runtimes. The
  runtimes need a command, ports (port 0, the bound address reported by the readiness endpoint), and a
  published port only when an external target needs it; D2 adds those, with a reason each.
- D3 (reconciliation) uses `owned(ownership)` to find the labelled resources of a run after a restart.
- The rollback runs on cancellation too (`BaseException`), but a rollback awaited during cancellation can itself
  be interrupted; D2 must not rely on it alone for the cleanup of a cancelled run.

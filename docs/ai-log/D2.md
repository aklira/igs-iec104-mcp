# D2 — Test bench lifecycle

## Prompt

Task D2 of `IMPLEMENTATION.md` §14: the lifecycle of §6 with readiness, ports bound by the runtimes, a
graceful stop with a deadline, rollback of a partial creation, and evidence preservation. Done when a failure
injected at each lifecycle step leaves no owned resource behind, and two test benches run side by side.

## Summary

- `docker/plan.py`: a bench is planned before anything is created. The plan is data: the runtime's arguments
  (a station listens on port 0 and publishes its control API; a client gets its station's address), the points
  file in the runtime's form, and the limits. It refuses, by name and all at once: a point kind the runtime
  does not serve (Q-002), link parameters other than the defaults (Q-003), a connection that reaches an
  external target (X1), a connection across networks, and a client without exactly one connection.
- `docker/bench.py`: `start_bench` brings up the networks, then each station (create, copy its files, start,
  wait for readiness), then each client (the same, then wait until connected). `RunningBench` gives a control
  client per runtime and `stop`, which stops the clients and then the stations with a deadline, keeps each
  runtime's logs and record, and removes the owner's resources, even when a stop fails. A failed start keeps
  the logs and records of its containers, then rolls back through D1's creation block. The checkpoint of each
  step is a test hook.
- `docker/adapter.py` and `docker/specs.py`: the control port is published on 127.0.0.1 at a port the engine
  picks; the token and the points are copied into `/run/igs` (created by the image, owned by UID 10001) with
  the archive interface, before the container starts (files 0400). No bind mount, no volume, no environment
  variable carries the token. `part_of` reads an instance back from a resource name.
- `docker/runtime.Dockerfile`: the runtime user has the fixed UID and GID 10001.
- `docker/bench.py` writes a manifest at the start (the bench, the run, the requested image, its resolved
  identity, the networks, the runtimes).
- `.github/workflows/ci.yml`: the integration job builds the runtime image and exports `IGS_RUNTIME_IMAGE`.
- D-016 records the lifecycle. Q-003 is opened (the runtime takes no link flags). Q-002 records the refusal.
- Correction: the earlier records said the upstream `PointValue` has eleven kinds. It has ten (see D-016).

Dependencies: none new. The Docker SDK (B1) and the controller's own runtime client (`runtime/api.py`,
`runtime/process.py`).

## Verification

- Unit tests (`tests/unit/test_docker_plan.py`, 13 tests): the link defaults equal the upstream defaults; the
  basic pair is planned with its station and its client; the arguments of a station and of a client; the event
  buffer; each refusal (kinds, link parameters, cross-network, external target, missing and double connection,
  runtime limits) with its name; every problem reported together.
- Integration tests (`tests/integration/test_docker_bench.py`, 4 tests) against Podman, with the runtime image
  built from `docker/runtime.Dockerfile`:
  - the basic pair comes up: the station reports a bound address on `0.0.0.0`, the client is connected, the
    owner holds three resources; the stop is graceful (exit status 0 for both), removes the three, keeps the
    logs and records, and the control token appears in no kept file;
  - a failure injected at each of the nine steps (image, the network, create, start, and ready of the
    station; create, start, ready, and connect of the client) leaves no owned resource, and keeps the station's logs for a
    failure after the station started;
  - two benches run side by side, with disjoint resources, and one stops without touching the other;
  - a bench that does not plan creates nothing.
- Integration tests, D1 and D2 together: 12 pass; no labelled resource is left behind.
- Gates: `ruff format`, `ruff check`, `mypy` (strict, 49 source files), unit tests (194 pass), the licence check.
- The CI integration job runs the Docker tests on Docker, with the image built in the job. That run has not
  happened yet.

## Size

## Correction after the CI run of a755cee

- Docker does not publish a port of a container on an internal network, so the control port published by each
  runtime was never reachable from the host (the CI showed `has no published control port`). The bench network
  stays internal. Each runtime is now reached through a relay container on a separate control network, which
  publishes the port (D-018). The relay image is built from `docker/relay.Dockerfile` (the Python base pinned by
  digest) and runs `docker/relay.py`, standard library only.
- The bench now has one more network (`control`) and two more containers per bench (the relays). The runtime
  publishes no port. The tests check it.
- The failure-injection test runs twelve steps, including `network:control` and each `relay:` step; it takes
  about four minutes on Podman. The CI job has no time limit beyond the default.
- Verified with Podman: the four bench tests and the eight adapter tests pass, and no labelled resource is left.
  Docker has not been run here; the CI run is the check.

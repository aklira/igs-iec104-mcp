# M3 — Confirmation of operations on external targets

## Prompt

Task M3 of `IMPLEMENTATION.md` §14: the policy of §9 for operations on external targets. Depends on M2 and X1. Produce:
allowed operations, elicitation, and a recorded confirmation. Done when tests show a state-changing operation refused
when not allowed, refused without confirmation, and recorded when confirmed.

## Summary

- `scenarios/confirmation.py` (new): the decision for a state-changing operation to an external target. A client that
  supports elicitation is asked, and only an accepted answer with `confirm` set to true is a yes; a client that cannot
  be asked is answered by a reviewed opt-in of the target, if there is one; otherwise the operation is refused. The
  `Gate` is the handler of `send_command` for a run: it refuses a target that does not allow the command, asks, and
  journals each decision.
- `models/target.py`: `OptIn` (reviewer, review date, operations) and `ExternalTarget.opt_in`. An opt-in covers only
  allowed, state-changing operations. The bench schema is regenerated.
- `scenarios/engine.py`: `StepUnsupported`, a step outcome for what the run does not carry out. A confirmed command is
  unsupported, because external connections are not made yet.
- `scenarios/runner.py`: `start` takes the run's confirmer; the gate is the handler of `send_command`.
- `server.py`: `scenario_run` gives the run the client's session. Its description says a command to an external target
  is confirmed by a person when the client supports it.
- D-038 records the decisions, and what is not in M3.

Dependencies: none new (`mcp` already listed; the elicitation types come from it).

## Verification

- `tests/unit/test_run_confirmation.py` (16 tests) passes: a command confirmed by a person is journaled as confirmed and
  is unsupported; declined, it fails; with no elicitation, a reviewed opt-in confirms it, and without one it is refused;
  elicitation is preferred to an opt-in; a managed client's command is unsupported and not gated; a target that does not
  allow the command is refused at start; the opt-in's rules; the elicitation answer is a yes only when accepted with
  `confirm` true, and a client that does not answer confirms nothing.
- `tests/integration/test_mcp_confirmation.py` (2 tests) passes on Podman with the runtime and relay images of this
  repository: a real MCP client answers the question and the run journals `accepted` with `how` set to `elicitation`;
  a client without elicitation gets a refusal (`how` set to `none`), the step fails, and the bench is removed.
- The unit suite and the MCP stdio test pass (370 tests). The run and reconciliation integration tests still pass, and
  no managed container is left.
- Gates: `ruff format --check`, `ruff check`, `mypy` (strict, 79 source files), and the schema check.

## Decisions

- D-038: the order of the sources of the decision; the opt-in's rules; the journal; the outcome of a confirmed command;
  the timeout; what is not in M3.

## Open

- A confirmed command reaches no peer: the planner refuses external connections. Lifting that refusal is a decision
  for the maintainer, and it belongs with the external connections (X3 or a task after it).
- The other state-changing operations (set-point, clock synchronisation, counter freeze and reset) have no scenario
  step yet, so the gate covers `send_command` only.

## Points for the next tasks

- The confirmation shares the step's timeout, which defaults to 10 seconds. A person needs longer; a scenario that
  expects a confirmation should set its timeout.
- The question is asked in the run's task, after `scenario_run` has returned. A client that disconnects during the
  question gets a refusal, recorded as no answer.

## Size

About 230 lines of the confirmation module, the target model, the runner, the server, and the engine, and about 270
lines of tests.

# E5 — Restart and reconnect primitives

## Prompt

Task E5 of `IMPLEMENTATION.md` §14: restart and reconnect primitives. Depends on D2, E1, and U2. Done when an
end-to-end scenario restarts the server and asserts that the client reconnects, starts the transfer, and interrogates
again.

## Summary

- `scenarios/actions.py`: the handlers of the instance actions over a `Bench` (the control API of each instance, the
  clients of each station, and how an instance stops and starts): `wait_connection`, `start_transfer`,
  `wait_transfer_started`, `general_interrogation`, `update_point`, `stop_instance`, and `start_instance`.
- `models/scenario.py`: `start_transfer` is a new action; `stop_instance`, `start_instance`, and `update_point` gain a
  `timeout`. The scenario schema is regenerated.
- `runtime/local_bench.py`: `LocalBench`, one station and one client as local processes. The addresses are fixed when
  the bench is made, so a restarted instance answers on the same ones.
- D-030 records the decisions, the limits, and the managed-bench restart that is not in E5.
- The E3 test of the cleanup deadline now uses a parallel cleanup step, since `stop_instance` has a timeout of its own.

Dependencies: none new.

## Verification

- `tests/unit/test_scenario_actions.py` (8 tests, against a fake bench): a connection wait passes when the client comes
  up; a station is an error; the transfer is requested and awaited; an interrogation ignores an earlier end; a stop
  waits for its clients to disconnect, passes at once without a connected client, and times out when a client never
  disconnects; an update waits for the stored value.
- `tests/integration/test_restart_scenario.py` (2 tests, runtime binary built by `cargo test`): the station is updated,
  restarted under the scenario, and the client reconnects, starts its transfer, interrogates again, and reads the
  restarted station's value (the value of the points file, not the one before the restart). A reconnect that does not
  come in time times out, and the cleanup starts the station again.
- The restart, runtime-scenario, and milestone integration tests (6) pass three times in a row.
- Gates: `ruff format --check`, `ruff check`, `mypy` (strict, 62 source files), the unit suite (272 pass), and the
  schema check (`--check`).
- Found while testing: the E3 cleanup-deadline test relied on a stop step with no timeout; with the new timeout the
  test was checked against the barrier's deadline instead (the test passed after that change, and the stop's own
  timeout still applies to the stop).

## Decisions

- D-030: the actions and their waits; `start_transfer` (the library does not restart the transfer after a reconnect);
  the timeouts on the three actions; the local bench; the managed-bench restart is open.

## Points for the next tasks

- A managed (container) restart needs a fixed station port in the plan (D2): a restart with port 0 changes the port,
  and the client's target goes stale. It needs a decision on the port, then a restart of a member of the bench.
- `wait_connection` on a station is refused as an error; a wait on a station's connections (station events) is a later
  addition.
- The waits read the whole event log (`events()` with no cursor) for the interrogation, as the source does; a cheaper
  query would help long runs.
- E4 is done; V2 (redundancy) depends on E5 and U2 and is later in the plan.

## Size

About 170 lines of actions, 120 of the local bench, 60 of model changes, and about 330 lines of tests, which makes about
670 lines with the schema. That is above the roughly 400 lines of §2: the actions, their tests, and the first
end-to-end run form one contract, so the change is kept as one task.

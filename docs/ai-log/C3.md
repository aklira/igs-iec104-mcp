# C3 — Server role: points, simulation, command policy, observation

## Prompt

Task C3 of `IMPLEMENTATION.md` §14: point management, simulation with seeds and periods, the configured
command policy, a command log through the handler, the station's connection events (`ServerEvent`) in
the runtime's event stream, and the stop through `run_until` with its `ShutdownReport`. Done when the
tests cover accepted and refused commands, select-before-operate with selection expiry, seeded simulation
reproducibility, the connection events of a client that connects, starts, and leaves, a stop that reports
its connections, and a nonzero drop count of the server events that is reported.

## Summary

- Points: a point has a command policy (`unknown_address` by default, `refuse`, or `accept` on a single or
  double point) and an optional simulation (`toggle`, `ramp`, or `walk`, with a period, an increment, and a
  seed). Both are checked when the file is read, with a message that names the point.
- `simulate.rs`: a simulator whose step is a function of the step number and the seed (SplitMix64, no new
  dependency). Values stay on the grid and in the range of their kind. `drive` publishes the steps on the
  station at their period.
- `server_role.rs`: the policy handler judges each command by the policy of its point and queues the
  judgement without waiting (a bounded channel, counted when full). The handler runs on a connection's task,
  so it never blocks.
- `station_log.rs`: the station's own event log: connections, transfers, supersessions, closes, and the
  commands judged, each with a sequence number.
- `runtime.rs`: the station's event stream and its judgements are recorded into that log, and the losses of
  the queues are counted into it. The stop returns the library's `ShutdownReport` (`Stopped`).
- `api.rs`: `GET /v1/station/events` (station only).
- Settings: `--selection-timeout-ms` (30000 by default).
- Contract 1.2.0: `contracts/station-events.schema.json` and the route. The contract test found that
  connection identities start at zero; the schema now says so.

Dependencies: none added.

## Verification

- Unit (Rust): the simulator (toggle, double toggle, normalized and scaled ramps wrapping, a seeded walk
  repeating and following its seed, a walk staying in range, the value of every step accepted by its kind),
  the paused-clock driver (each step published at its period), the points validation, and the station log
  (sequence, losses, reads).
- Integration (`tests/station.rs`, 5 tests), against the upstream controller: the accepted command is
  confirmed, the refused one is a negative confirmation, and a point without a command gives cause 47; the
  station log holds each judgement; a selection that waits longer than the time-out is refused on its
  execution; a client that connects, starts, and leaves is reported in that order, with the end of the
  connection as a transport end; a stop reports the connection that was open; a burst of connections into a
  one-event stream loses events, and the station reports the count (repeated six times without a failure).
- Python: the contract test covers the station route and the station events schema is checked as a schema.
- Gates: formatting, clippy with warnings as errors, all tests, `cargo deny`, and the Python checks; the image
  builds with Podman.

## Decisions

## Points for the next tasks

- An accepted command does not change its point: the controller updates it. A simulated station that must
  show the effect of a command needs that update, from the controller or from a later rule.
- The command policy is per point. Per command type, for the same point, is not in the file yet.
- The loss count is read every 50 milliseconds, so a value read in that gap can be a little old.
- The station's events and the client's events have separate logs, with separate routes.
- The simulation and the points file are read from the configuration file; the schema of that file is part of
  C4.

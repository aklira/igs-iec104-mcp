# S3 — Minimal Python control path

## Prompt

Task S3 of `IMPLEMENTATION.md` §14: a Python function that starts a server and a client runtime as
local processes or containers, runs the milestone 1 sequence (connect, start the transfer,
interrogate, update a point, observe it, stop), and stops both. Done when the milestone 1 criterion
passes in an integration test. Record what the spike showed about shutdown, connection observation,
and event coverage.

## Summary

- The runtime prints its bound addresses once on standard output, as one JSON line (D-008). It did
  not before: a controller that gives port 0 could not learn the port. This is the only change to
  the runtime. The line is printed after the control listener and the station are bound.
- `src/igs_iec104_mcp/runtime/process.py`: `LocalRuntime` starts a runtime as an `asyncio`
  subprocess, reads the first stdout line for its addresses, drains standard error into a bounded
  tail (for diagnostics), and stops it with SIGTERM, then kills it after 20 seconds. Stopping a
  runtime that never started returns no exit code, so a failed start does not hide its cause.
- `src/igs_iec104_mcp/runtime/api.py`: `ControlClient`, an `httpx` client for the control API.
  It raises `ControlApiError` for an error status. It is a spike: it follows the current routes,
  and task C1 fixes them.
- `src/igs_iec104_mcp/runtime/asdu.py`: reads the single-point values of an ASDU in its two forms
  (individual objects and sequence). The point image of task C2 replaces it.
- `src/igs_iec104_mcp/runtime/milestone1.py`: `run_milestone_one(binary, directory)` starts the
  station (points file with point 1 at `false`) and then the client, runs the four steps, and stops
  both, the client first. Each step takes the client's event cursor before it acts, so an earlier
  answer cannot satisfy a later step. A timed-out step is recorded as a failed observation rather
  than raised, and the processes are stopped in any case.
- `tests/integration/test_milestone1.py`: runs the milestone with the binary named by
  `IGS_RUNTIME_BINARY`. Locally it skips without the variable; in CI it fails.
- `tests/unit/test_asdu.py`: the reader, on the forms the runtime prints and on the errors.
- CI: a new `integration` job builds the runtime and runs the integration tests.

Dependencies: `httpx` (approved at B1). No new dependency.

## Verification

- `uv run pytest tests/unit`: 33 tests pass (5 new, for the reader).
- `uv run pytest tests/integration` with the built binary: the milestone passes.
- The sequence run directly, with its timings:

  | Observation | Result |
  | --- | --- |
  | interrogate | point 1 answers `False`, as the file says |
  | update_point | the station stores `True` |
  | observe_update | one spontaneous ASDU after the update |

  Step durations: start 0.047 s, connect 0.049 s, start transfer 0.002 s, interrogate 0.056 s,
  update 0.006 s. Both runtimes exit with status 0.

## What the spike showed

**Shutdown.**

- A runtime stops within a few milliseconds when SIGTERM arrives, with exit status 0, and the
  controller never needed to kill one.
- The order matters less than it could: a station stopped while a client was transferring took
  3.5 ms, exited 0, and the client recorded `disconnected` after the last ASDU. The five-second
  grace was not reached.
- The milestone stops the client first, so the station's drain was not exercised in the milestone
  itself; the separate measurement above covers it.

**Connection observation.**

- A controller learns the addresses from the first stdout line, and the connection from
  `GET /v1/ready` (`connection: up`). On loopback the connect step took 0.049 s from the start.
- Nothing observed a failed connection in the milestone. The `connect_failed` event was exercised
  only by the runtime's own test (S1).

**Event coverage.** The client's events in the milestone were `connected`, `transfer`, `asdu`, and
`transmitted`. Not covered by this spike: `disconnected` (seen in the stop measurement only),
`connect_failed`, `rejected`, `discarded`, `unacknowledged`, and `closed`. The events of the
station (connections, transfers) are not in the control API yet (task C3).

**Points of the spike.**

- The reader decodes single-point values only. A value of another type shows as nothing, not as an
  error, so a milestone that needs another type cannot pass until C2 adds the point image.
- `ControlClient` sends the update body and the routes as the runtime has them today. Any change
  of a route breaks this client, which is intended for a spike and is why C1 comes next.
- A POST without a body is refused by the runtime's JSON extractor before its role check (S2). The
  client always sends a body.

## Open points

- The milestone uses local processes. The Docker adapter (D1) and containers are not in S3.
- The control API still has no credential (§3). C1 adds it.
- The client's event buffer is bounded (1024 events by default). The spike runs far fewer, so
  nothing was dropped (`dropped: 0`).

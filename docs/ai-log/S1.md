# S1 — Runtime, client role

## Prompt

Task S1 of `IMPLEMENTATION.md` §14: run the runtime as a client with a minimal HTTP control API
(readiness, start transfer, general interrogation, and an event list). Done when, against the
upstream demo server, the API starts the transfer, runs an interrogation, and returns its answers.

## Summary

The runtime (`runtime/igs-iec104-runtime`) is now a library with a binary:

- `config`: the command line, parsed by hand. `--connect` is required; `--common-address` is 1 to
  65534; `--control` defaults to `127.0.0.1:0`; `--event-capacity` defaults to 1024. With no
  argument the binary prints its identity, as in B2, so that the image check of CI still holds.
- `client_role`: the owner task. It is the one task that reads the client's events and makes its
  requests. It records each event and keeps the connection and transfer status. The client is
  configured with `OfflineRequests::Discard` (§7).
- `events`: a bounded event log. Each event has a sequence number, the observation time (Unix
  milliseconds, UTC), and a kind. The oldest events are dropped and counted when the log is full.
  The reader can detect a gap from `first_seq`.
- `runtime`: binds the control listener first, so the control address is known before serving. The
  listener is separate from the IEC 104 traffic (§3).
- `api`: `GET /v1/ready`, `POST /v1/transfer/start`, `POST /v1/interrogation/general`, and
  `GET /v1/events?after=N`. A POST answers `202` once the client has queued the request; its outcome
  comes as events. A request that cannot be queued answers `503`.
- The binary stops on Ctrl-C or on SIGTERM. SIGTERM matters in a container: PID 1 ignores a signal
  it does not handle, so `docker stop` (or `podman stop`) would otherwise wait for the kill timeout.

Dependencies added, all approved: `axum` 0.8, `serde` (derive), `serde_json`, `tracing`,
`tracing-subscriber`, and `tokio` (agreed). Also `igs-iec104-codec` and `igs-iec104-link`, from the
same upstream repository at the same revision (`e91ecc8`), because the runtime names their types
(`CommonAddress`, `Qoi`, `Asdu`, `TransferState`). §4 names both crates as part of the upstream.

## Verification

Automated (`cargo test --workspace --locked`): 20 unit tests and 2 integration tests.

- `tests/client_role.rs`, first test: an upstream server runs in the same process. The runtime
  reaches `connection: up`, starts the transfer (`started`), runs a general interrogation, and the
  events hold the answers: the single point (type 1) with cause 20, and the termination (cause 10).
  Every ASDU carries its hexadecimal encoding.
- `tests/client_role.rs`, second test: with no station listening, the client reports
  `connect_failed`. A request is accepted (`202`), then reported as `discarded`, and the status stays
  `down` and `stopped`.

Manual, against the upstream demo station (`igs104-server`, built from `e91ecc8`, `--bind
127.0.0.1:2404 -c 1`):

- The runtime connects; `GET /v1/ready` reports `connection: up`.
- `POST /v1/transfer/start` gives `202`; the events show `pending_started`, then `started`.
- `POST /v1/interrogation/general` gives `202`; the events hold the station's answers: the points
  with cause 20 (types 1, 3, 9, 11, 13), the confirmation (type 100, cause 7), and the termination
  (type 100, cause 10). Spontaneous changes (cause 3) of the simulation arrive too.
- The event log reports `first_seq: 1`, `dropped: 0`.
- SIGTERM stops the runtime with exit status 0 at once (checked on a runtime without a station).

Gates: the Python gate passes; the Rust gate passes (`cargo fmt --check`, `clippy -D warnings`,
`cargo test`, `cargo deny check`). The image builds with Podman and prints its identity, running as
uid 999.

## Decisions and open points

- The decoded form of an ASDU is not in the control API yet: each ASDU is reported by its header
  and its hexadecimal encoding. The decoded form, and the schema of the events, are fixed in C1.
- The control credential (§3) is not implemented. The control API binds loopback by default, and
  nothing in S1 needs a credential. C1 adds it, and it must stay out of logs and reports.
- Requests are answered by the owner task, which does not read events while it sends a command. The
  upstream channels are bounded, so a flood of requests could make the owner and the client wait on
  each other. C2 must check this and redesign the owner if needed.
- The API routes have no stable contract until C1 (the code says so).

# C1 — Runtime API and event contract

## Prompt

Task C1 of `IMPLEMENTATION.md` §14: write the runtime API contract (an OpenAPI document) and the
event contract (a JSON Schema), both versioned in `contracts/`, and contract tests on both sides.
Done when the Python client and the Rust server pass the contract tests.

The decisions taken with the maintainer before the work: approve `jsonschema` and
`openapi-spec-validator` for the tests; a control token read from a file; the decoded ASDU values
left to C2.

## Summary

- `contracts/runtime-api.yaml`: OpenAPI 3.1, version 1.0.0. The routes of the client and the station,
  with every status they can answer: 202 and 503 for a request to the client, 200 and 400 to 500 for
  points, 401 for a missing or wrong token, 404 for an unknown point, and 409 for a route of the other
  role. Bearer authentication applies to every route.
- `contracts/events.schema.json`: the ten kinds of event of the client, each with its own fields
  (no field outside them), the transfer states, and the ASDU header with its hexadecimal encoding.
- The runtime: `--control-token-file` is required; the token is checked on every request in a layer
  that runs before routing; the readiness body carries `contract` and `role`. The token is redacted in
  its `Debug` form.
- Python: `write_control_token` writes a token file (mode 0600); `ControlClient` sends the token;
  the milestone runner passes it to both runtimes.
- Tests: Python, 38 unit tests (the contract documents among them) and 2 integration tests (the
  milestone, and the contract of every route). Rust, 35 unit tests (the token and the configuration
  among them), and 2 + 3 + 3 integration tests (the client role, the contract, and the station role
  with the authentication test).

## Decisions

- D-009: the contract, the token, and the validators.
- D-010: the decoded ASDU values come with C2.

## Verification

- The OpenAPI document is valid (openapi-spec-validator, with its file as base URI); the events
  schema is a valid 2020-12 schema.
- The Python integration test starts a station and a client, and checks each response against the
  documented status and schema. It also checks that a request without the token gets a 401 with the
  `WWW-Authenticate: Bearer` header.
- The Rust contract test serializes one event of each kind and checks it against the schema, with a
  reader of the subset of JSON Schema the contract uses. A negative test checks that the reader
  refuses an event outside the contract.
- The image builds with Podman and prints its identity.

## Points for the next tasks

- The contract does not yet describe the decoded values (D-010) or the station's connection events
  (C3, from the upstream `ServerEvent` stream).
- The Rust reader of the schema does not check `pattern` (the hexadecimal encoding); the Python
  validator does.
- The token is read once, at start. A rotation needs a restart of the runtime; no task needs
  rotation yet.
- The contract is not yet used to generate code. The plan asks for contract drift checks from the
  published models (C4); C1 has none.

## Size

The change is about 900 lines (the two contracts, the runtime token and the tests, the Python
checks). It is above the roughly 400 lines that §2 allows; as with S1 to S3, it is one change because
its acceptance needs the contract and both sides together.

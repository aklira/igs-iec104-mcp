# M2 — Scenario and run tools

## Prompt

Task M2 of `IMPLEMENTATION.md` §14: the scenario and run tools, asynchronous runs, pagination, and resources. Depends on
M1, E3, and D2. Done when the milestone 5 criterion passes with a real MCP client in CI: a real client creates and
executes a test bench scenario.

## Summary

- `scenarios/runner.py`: `Runner` starts a run of a scenario on its Docker bench, follows it in a task, journals each
  verdict as it is known, cancels it on request, enforces the execution time of its instances, and removes its bench
  afterwards. `DockerEngine` starts benches through the D2 lifecycle; `NoEngine` refuses them when the server has no
  images.
- `server.py`: the five run tools (`scenario_run`, `run_get`, `run_list`, `run_events`, `run_cancel`), and the
  `--runtime-image` and `--relay-image` options.
- `scenarios/engine.py`: `execute` takes an observer of the verdicts.
- `scenarios/actions.py`: an update completes when the connected clients hold the new value.
- `examples/scenarios/interrogation-and-spontaneous-update.yaml`: requests the client's transfer first, and checks the
  update by its value and cause.
- `definitions/service.py`: the error codes `invalid_state`, `unsupported`, and `engine_unavailable`.
- D-033 records the decisions, the limits, and what is not in M2.

Dependencies: none new (the Docker SDK and `mcp` are already listed).

## Verification

- `tests/integration/test_mcp_run.py` (the milestone 5 criterion) passes on Podman with the runtime and relay images
  built from this repository: a real MCP client creates the bench and the scenario, runs the example, follows the run to
  `passed` with six journaled verdicts, lists it, and finds the bench's containers removed (35 seconds).
- `tests/integration/test_mcp_stdio.py` lists the fourteen tools.
- The whole integration suite ran against Podman and the runtime binary (23 tests, 5 minutes): 22 passed, and the one
  failure was the expected tool list, which was corrected; the stdio test then passed on its own.
- `tests/unit/test_scenario_runner.py` (10 tests) passes three times in a row with warnings as errors, together with the
  action tests.
- Gates: `ruff format --check`, `ruff check`, `mypy` (strict, 71 source files), the unit suite (322 pass), and the
  schema check.
- Found while testing: (1) the adapter refuses an image by tag (§6 names images by digest), so the server now checks
  both images by identity before a run, and the test passes identities as an operator would; (2) the example scenario
  waited for a transfer that nothing started, and its `expect_point` could miss the update, since the station's
  spontaneous update could be recorded before the step's cursor; the update now completes when the client holds the
  value, and the example checks it with `assert_point`.

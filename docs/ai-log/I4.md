# I4 — Installer: build and image identities

## Prompt

Task I4 of `IMPLEMENTATION.md` §14 (Phase I, issue #1): `scripts/install.sh --engine auto|podman|docker [--dry-run]
[--project-dir PATH]`. It runs the preflight, `uv sync --locked`, builds the runtime and relay images with the engine,
reads each image identity, creates the project directory, and writes a state file with absolute paths and identities.
No system package, `sudo`, or group change. Done when `--dry-run` changes nothing, a second run changes nothing, the state
holds identities and absolute paths, and tests run the script with a stub engine and a stub `uv` on `PATH`.

## Summary

- `scripts/install.sh`: the steps above. A dry run prints them and changes nothing. A failed preflight prints its report
  and stops with exit 1. A missing `uv` stops with exit 2, as an option error does.
- `tests/integration/test_install.py`: five tests. The engine is a Unix socket that answers `/version` and `/_ping` as
  Podman does, and the engine CLI is a stub that records each build and gives each image a deterministic identity. The
  `uv` stub makes `uv sync` a no-op and forwards every other call to the real `uv`. The tests skip without `uv`,
  `pkg-config` or the OpenSSL development files, and fail in CI.
- `DECISIONS.md`: D-059 (the engine CLI for the builds, the identity form, the state location, the prerequisites).
- `IMPLEMENTATION.md`: I4 ticked in §16.

## Found while testing

- The Docker SDK requires the `ApiVersion` key in the `/version` answer; the first version of the stub omitted it, and
  the preflight reported the socket as an invalid daemon. The stub now sends it, as Podman does.
- Podman reports an image identity without the `sha256:` prefix. The installer normalises it.

# I9 — CI installation on a fresh checkout

## Prompt

Task I9 of `IMPLEMENTATION.md` §14 (Phase I, issue #1): a CI job on a fresh checkout that runs the installer twice (the
second run changes nothing), the doctor with `--run-bench`, and the registration tests. It uses no image, cache, or
configuration left by another run. Done when the job passes on `main` and on a pull request; the WSL2 check is not in CI.

## Summary

- `.github/workflows/ci.yml`: a job `install` on `ubuntu-latest`. It checks out without persisting credentials, installs
  the OpenSSL development files, sets up `uv` with its cache disabled, and then:
  1. runs `scripts/install.sh --dry-run`, and checks that it created neither the project nor the state;
  2. runs the installer, with `--engine docker` (the runner's engine);
  3. runs it again, and checks `state unchanged` and that the state file is byte-identical;
  4. checks the state: the engine, the two `sha256:` identities, and the absolute paths;
  5. runs the server's handshake (`doctor --server-only`);
  6. runs `doctor --run-bench --json`, checks `bench-run` and `bench-cleanup`, and checks that no container or network
     with the managed label is left;
  7. runs the registration tests of `tests/integration/test_install.py` (stub client CLIs).
- `IMPLEMENTATION.md`: I9 is not ticked. It is ticked only after the job passes on `main`, which needs the merge.

## Choices

- Docker, not Podman, in CI: the runner has Docker. Podman is tested on the maintainer's WSL2 host, as the platform matrix
  states. The job uses `--engine docker` so that the engine it checks is the one it runs.
- No `actions/cache`: each job starts from an empty runner, and the installer builds both images from the Dockerfiles.
- Client registration is not run against the runner's client CLIs, because they are not installed there. Its behaviour is
  tested with stub CLIs, as the registration tests do.

## Verification

- The workflow parses as YAML (`ruamel.yaml`), with the new job's ten steps in order.
- The state check of step 4 was replayed locally on an identity state written by the installer, and it passes.
- `scripts/install.sh` passes `bash -n`. The job itself runs only on GitHub; its first run is the pull request's.

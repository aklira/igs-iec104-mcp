# M1 — MCP server over stdio

## Prompt

Task M1 of `IMPLEMENTATION.md` §14: the MCP server over stdio, stdout reserved for MCP messages, stable error codes,
and the definition tools of §9. Depends on B1 and C4. Done when an MCP client test lists the tools and validates a
definition.

## Summary

- `server.py`: `create_server(project)` registers the nine definition tools on `MCPServer`; `main` runs it over stdio,
  with its logs on stderr. `__main__.py` makes `python -m igs_iec104_mcp --project DIR` the entry point.
- `definitions/service.py`: the business logic of the tools (validation, creation, reading, updates with revisions,
  pages), with the stable error codes (`ServiceError`).
- `definitions/store.py`: `InvalidName` and `NameMismatch`, two kinds of `StoreError`, so the service can tell the
  failures apart.
- D-031 records the decisions, including the code position after the SDK's prefix and the pagination by name.

Dependencies: none new (`mcp` is already listed in `pyproject.toml` and §3).

## Verification

- `tests/unit/test_mcp_service.py` (18 tests): validation of a bench (valid, an extra field, text that is not YAML), of
  a scenario with and without its bench in the project, and of a scenario naming an unknown instance; creation,
  reading with the revision, a repeated create, a missing definition, bad names, invalid text, a name that does not
  match its file, updates with a current and a stale revision, pages with a cursor, a limit out of range, and the
  server's exit with status 2 when the project directory is missing.
- `tests/integration/test_mcp_stdio.py` (2 tests): a real MCP client starts the server as a process, lists the nine
  tools, validates a bench and an invalid one, stores a bench, reads it back, and gets `already_exists` and
  `not_found` as codes.
- Gates: `ruff format --check`, `ruff check`, `mypy` (strict, 66 source files), the unit suite (290 pass), the MCP
  integration tests (2 pass), the schema check, and the licence policy (58 distributions, none outside it).
- Found while testing: the SDK prefixes a tool error's text with `Error executing tool <name>: `, so the code is not
  the first word of the text. The test reads the code after the prefix, and D-031 records it.

## Decisions

- D-031: the entry point; the nine tools; the results and the error codes; the cursor by name; the two store errors.

## Points for the next tasks

- M2 adds the run and instance tools, and it must not block the event loop with the Docker calls (the definition
  tools block only on short file I/O under a lock).
- The stdio test starts the server through `PYTHONPATH`; if the project is ever installed, the test can drop it.
- X1 adds `target_validate`, and M4 adds Streamable HTTP with its authentication.

## Size

About 230 lines of service and server, about 40 of store and entry point, and about 300 lines of tests. That is above
the roughly 400 lines of §2 with the tests, but the tools and their service are one surface, and splitting them would
leave the tools without their logic.
